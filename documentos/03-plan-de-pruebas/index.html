    Plan de pruebas de Vigía (Unidad II)¶

    Plan de una página según la estructura de ISO/IEC/IEEE 29119-3 (plan de pruebas del proyecto). Cubre las pruebas de la propia plataforma Vigía en la versión 2.0.

    Campo Contenido
    Identificador PP-VIGIA-2.0 · versión 1.0 · 16/11/2026
    Responsables Víctor Carretero (QA, aceptación, E2E, UAT) · Gerald Zevallos (unitarias, integración, sistema, no funcionales)
    Aprobación Ambos integrantes, por PR; se revisa en cada semana de la Unidad II

    1. Contexto y alcance¶

    Qué se prueba: la API REST (FastAPI) y la interfaz web de Vigía, con estas funciones: - historias de usuario; - casos de prueba MANUAL, API y SQL, y suites; - corridas de prueba con evidencia; - tickets de defecto; - matriz de trazabilidad y métricas; - integraciones (JUnit XML, GitHub Issues, Discord o Slack); - cuentas, proyectos, roles y notificaciones (regresión de la v1.0).

    Qué no se prueba: - los sistemas que los usuarios prueban con Vigía; - la infraestructura de Microsoft Azure, salvo con smoke tests tras desplegar; - Google, GitHub y Discord, que se reemplazan por dobles de prueba.

    Base de prueba: FD03 (RF01–RF35, RNF01–RNF15, RN01–RN20), las historias HU-01 a HU-13 con sus criterios de aceptación y FD04 (arquitectura).

    2. Riesgos que guían la prueba¶

    Riesgo de producto Prob. Impacto Respuesta de prueba
    Un caso SQL deja cambios en la BD objetivo Baja Muy alto Unitarias y de mutación del motor y la política SQL; integración con Oracle real
    Un caso API alcanza la red interna (SSRF) Media Alto Particiones y valores límite de IP y dominios; DNS rebinding y redirecciones; Semgrep
    Un usuario ve o cambia datos de otro proyecto Media Alto Tabla de decisión rol × acción; pruebas de API por rol
    Un fallo no genera ticket o se pierde la evidencia Media Alto Integración corrida → ticket; BDD de HU-06 y HU-07
    La interfaz falla en algún navegador Media Medio E2E en Chromium, Firefox y WebKit
    Lentitud con un aula completa Media Medio Locust con 20 usuarios
    Vulnerabilidades en dependencias Media Alto Snyk en cada PR

    3. Estrategia¶

    Nivel Técnica de diseño Herramienta Carpeta Quién Cuándo corre
    Unitarias Particiones de equivalencia, valores límite, tablas de decisión pytest + pytest-cov tests/unit Ambos Cada push y PR
    Mutación Mide la efectividad de las unitarias mutmut tests/unit Ambos Semanal
    Integración API + ORM + migraciones con BD real pytest + PostgreSQL y Oracle en servicios de CI tests/integration Gerald Cada PR
    Sistema Flujos completos sobre Docker Compose pytest + httpx tests/system Gerald Cada PR
    Interfaz (E2E) Casos de uso, pairwise navegador × rol Playwright tests/ui Víctor Cada PR
    Aceptación Escenarios Gherkin en español desde los criterios pytest-bdd tests/acceptance Víctor Cada PR
    UAT Guion de tareas con usuarios reales Cuestionario SUS docs/uat Víctor Semana 6
    No funcionales Carga, análisis estático y dependencias Locust, SonarCloud, Semgrep, Snyk tests/load Gerald Carga: semana 5 · estático: cada PR

    Las pruebas unitarias usan SQLite; las de integración y sistema usan PostgreSQL y Oracle. Todas usan dobles de prueba para Google, GitHub, Discord y el correo. Ninguna prueba envía correos reales ni llama a servicios externos.

    4. Criterios¶

    • Entrada a la prueba de una historia: la historia tiene criterios Dado/Cuando/Entonces aprobados y el PR compila.
    • Salida para hacer el merge de un PR (DoD):
    • el 100 % de las pruebas en verde;
    • cobertura de líneas mayor o igual al 80 %;
    • Quality Gate de SonarCloud aprobado;
    • 0 hallazgos ERROR en Semgrep y 0 vulnerabilidades high en Snyk;
    • escenarios BDD de la historia en verde.
    • Salida para el release v2.0.0:
    • todo lo anterior;
    • mutation score mayor o igual al 70 % en los módulos críticos;
    • E2E en verde en 3 navegadores;
    • p95 menor a 1.5 s con 20 usuarios;
    • SUS mayor o igual a 70;
    • 0 defectos ALTA abiertos.
    • Suspensión y reanudación:
    • si el pipeline de main está en rojo, no se hace merge de ningún PR hasta corregirlo;
    • si falla el entorno de Oracle en CI, se marca la corrida como bloqueada y se reanuda al restaurarlo.

    5. Entorno y datos¶

    • CI: GitHub Actions con Python 3.11 y 3.12, servicios de PostgreSQL 16 y Oracle 23ai Free.
    • Sistema y E2E: Docker Compose.
    • Producción: la VM de Azure; solo smoke tests después de cada despliegue.
    • Datos:
    • fixtures generados en cada prueba;
    • claves y tokens de prueba creados al vuelo (secrets.token_urlsafe);
    • ningún dato personal real.

    6. Entregables y métricas¶

    Reportes en cada corrida: se publican en el resumen del job, como artifacts y en GitHub Pages (§8.16 del handoff): - cobertura; - mutación; - JUnit y Allure; - Playwright; - BDD como documentación viva; - SonarCloud, Semgrep y Snyk.

    Métricas que se siguen: - tasa de aprobación; - cobertura; - mutation score; - defectos por severidad; - MTTR; - p95; - puntaje SUS.

    Al cierre: informe de finalización de pruebas (ISO/IEC/IEEE 29119-3) en la semana 6.

    7. Cronograma¶

    Semana Pruebas que se agregan
    1 Análisis estático con reportes y corrección de hallazgos ✔
    2 Reorganizar tests/ por nivel; cobertura y mutación con reportes
    3 Integración con PostgreSQL y Oracle; sistema con Compose; smoke test del release
    4 E2E con Playwright en 3 navegadores
    5 Aceptación BDD; carga con Locust
    6 UAT con compañeros y SUS; informe de finalización
