    Backlog Unidad II — historias de usuario (INVEST)¶

    Rumbo: Opción 2 recortada (gestor de pruebas MANUAL + API + SQL, con historias, trazabilidad y corridas) + automatizaciones obligatorias + reto con 3 integraciones.

    Cada historia es Independiente (se entrega sola), Negociable, Valiosa para un rol, Estimable (puntos), Small (cabe en una semana) y Testeable (criterios Dado/Cuando/Entonces que pasan a escenarios BDD).

    Detalle y criterios de aceptación¶

    HU-01 — Registrar una historia de usuario con su descripción y criterios de aceptación¶

    Como líder de QA, quiero registrar una historia de usuario con su descripción y criterios de aceptación, para tener requisitos verificables contra los cuales probar.

    Épica: E1 Historias · Puntos: 3 · Prioridad: Alta · Semana: 2 · Responsable: Gerald (API) · Víctor (UI)

    Criterios de aceptación:

    1. Dado un proyecto activo en el que soy líder, cuando guardo una historia con título, «Como/Quiero/Para» y al menos un criterio, entonces la historia aparece en el backlog del proyecto con estado «Pendiente».
    2. Dado el formulario de nueva historia, cuando intento guardarla sin criterios de aceptación, entonces el sistema no la guarda e indica que falta al menos un criterio.

    HU-02 — Vincular un caso de prueba existente a una historia¶

    Como tester, quiero vincular un caso de prueba existente a una historia, para saber qué requisito verifica cada caso.

    Épica: E1 Historias · Puntos: 2 · Prioridad: Alta · Semana: 2 · Responsable: Gerald · Víctor

    Criterios de aceptación:

    1. Dado una historia y un caso del mismo proyecto, cuando vinculo el caso a la historia, entonces la historia muestra el caso en su lista de casos.
    2. Dado un caso de otro proyecto, cuando intento vincularlo, entonces el sistema rechaza el vínculo con un mensaje claro.

    HU-03 — Crear un caso de prueba MANUAL con pasos, datos de entrada y resultado esperado¶

    Como tester, quiero crear un caso de prueba MANUAL con pasos, datos de entrada y resultado esperado, para documentar pruebas que no se automatizan.

    Épica: E2 Casos · Puntos: 3 · Prioridad: Alta · Semana: 2 · Responsable: Gerald · Víctor

    Criterios de aceptación:

    1. Dado el formulario de caso con tipo MANUAL, cuando registro 3 pasos con su resultado esperado, entonces el caso se guarda con sus pasos en orden.
    2. Dado un caso MANUAL sin pasos, cuando intento guardarlo, entonces el sistema exige al menos un paso.

    HU-04 — Crear un caso de prueba de API con método, URL, cuerpo y aserciones de código de estado y JSON¶

    Como tester, quiero crear un caso de prueba de API con método, URL, cuerpo y aserciones de código de estado y JSON, para verificar servicios REST automáticamente.

    Épica: E2 Casos · Puntos: 5 · Prioridad: Alta · Semana: 2 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado un caso API GET a una URL permitida con aserción «status = 200», cuando lo ejecuto y el servicio responde 200, entonces el resultado es APROBADO y se guarda la respuesta como evidencia.
    2. Dado un caso API a una IP privada o a un dominio fuera de la lista blanca, cuando lo ejecuto, entonces el sistema lo bloquea (protección SSRF) y registra el motivo.

    HU-05 — Seguir usando los casos SQL existentes como «validación de datos»¶

    Como tester, quiero seguir usando los casos SQL existentes como «validación de datos», para no perder lo ya construido.

    Épica: E2 Casos · Puntos: 1 · Prioridad: Media · Semana: 2 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado un caso SQL creado en la Unidad I, cuando abro el módulo de casos, entonces aparece con tipo SQL y se ejecuta igual que antes, con ROLLBACK.

    HU-06 — Iniciar una corrida de prueba sobre una suite¶

    Como tester, quiero iniciar una corrida de prueba sobre una suite, para ejecutar un ciclo completo y registrar sus resultados.

    Épica: E3 Corridas · Puntos: 5 · Prioridad: Alta · Semana: 3 · Responsable: Gerald · Víctor

    Criterios de aceptación:

    1. Dado una suite con casos MANUAL, API y SQL, cuando inicio una corrida, entonces los casos automáticos se ejecutan solos y los manuales quedan «Por ejecutar».
    2. Dado una corrida en curso, cuando marco un caso manual como FALLIDO con comentario y captura, entonces el resultado y la evidencia quedan guardados con fecha y autor.

    HU-07 — Que se cree un ticket de defecto al fallar un caso¶

    Como líder de QA, quiero que se cree un ticket de defecto al fallar un caso, para que ningún fallo se pierda.

    Épica: E3 Corridas · Puntos: 3 · Prioridad: Alta · Semana: 3 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado una corrida en curso, cuando un caso termina FALLIDO, entonces se crea un ticket enlazado al caso, a la corrida y a la historia, con la evidencia adjunta.
    2. Dado un ticket abierto por un caso, cuando el caso pasa en una corrida posterior, entonces el ticket se marca «Listo para verificar».

    HU-08 — Ver la matriz de trazabilidad historia → caso → última ejecución → defecto¶

    Como líder de QA, quiero ver la matriz de trazabilidad historia → caso → última ejecución → defecto, para saber qué requisitos están cubiertos y cuáles fallan.

    Épica: E4 Trazabilidad · Puntos: 3 · Prioridad: Alta · Semana: 3 · Responsable: Víctor

    Criterios de aceptación:

    1. Dado un proyecto con historias, casos y corridas, cuando abro la matriz, entonces veo cada historia con sus casos, el último resultado y los defectos abiertos.
    2. Dado una historia sin casos, cuando abro la matriz, entonces la historia aparece resaltada como «Sin cobertura».

    HU-09 — Ver un dashboard con la tasa de aprobación, defectos por severidad y MTTR¶

    Como líder del proyecto, quiero ver un dashboard con la tasa de aprobación, defectos por severidad y MTTR, para decidir si una versión está lista para liberarse.

    Épica: E4 Métricas · Puntos: 3 · Prioridad: Media · Semana: 4 · Responsable: Víctor

    Criterios de aceptación:

    1. Dado al menos una corrida finalizada, cuando abro el dashboard, entonces veo la tasa de aprobación de la última corrida, los defectos por severidad y el MTTR en horas.

    HU-10 — Exportar el informe de una corrida¶

    Como líder de QA, quiero exportar el informe de una corrida, para entregar evidencia al cliente o al docente.

    Épica: E4 Métricas · Puntos: 3 · Prioridad: Media · Semana: 4 · Responsable: Víctor

    Criterios de aceptación:

    1. Dado una corrida finalizada, cuando pulso «Exportar», entonces descargo un informe con el resumen, el resultado por caso y los defectos (formato de informe de pruebas ISO 29119-3).

    HU-11 — Subir el JUnit XML de mi pipeline a Vigía¶

    Como desarrollador, quiero subir el JUnit XML de mi pipeline a Vigía, para ver las pruebas automatizadas de CI junto a las manuales.

    Épica: E5 Integraciones · Puntos: 3 · Prioridad: Media · Semana: 4 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado un token de proyecto válido, cuando el pipeline envía un JUnit XML, entonces Vigía crea una corrida con un resultado por cada testcase.
    2. Dado un XML mal formado, cuando se envía, entonces Vigía responde 422 y no crea la corrida.

    HU-12 — Crear un GitHub Issue desde un ticket¶

    Como líder de QA, quiero crear un GitHub Issue desde un ticket, para que el desarrollador vea el defecto en su repositorio.

    Épica: E5 Integraciones · Puntos: 3 · Prioridad: Media · Semana: 5 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado un ticket y un repositorio GitHub vinculado al proyecto, cuando pulso «Crear issue», entonces se crea el issue con el título, los pasos y el enlace al ticket, y el ticket guarda la URL del issue.

    HU-13 — Recibir una notificación en Discord o Slack cuando una corrida falla¶

    Como miembro del equipo, quiero recibir una notificación en Discord o Slack cuando una corrida falla, para enterarme sin entrar a la plataforma.

    Épica: E5 Integraciones · Puntos: 2 · Prioridad: Baja · Semana: 5 · Responsable: Gerald

    Criterios de aceptación:

    1. Dado un webhook configurado en el proyecto, cuando una corrida termina con fallos, entonces llega un mensaje con el nombre de la suite, los fallos y el enlace a la corrida.
    2. Dado el webhook responde con error, cuando se intenta notificar, entonces la corrida no se ve afectada y el error queda en el log.

    Definición de Hecho (DoD)¶

    • Criterios de aceptación cubiertos por escenarios BDD en verde.
    • Pruebas unitarias y de integración nuevas; cobertura del módulo ≥ 80 %.
    • static-analysis.yml en verde (Quality Gate aprobado, sin hallazgos ERROR/high).
    • Revisado en un PR por el otro integrante; el merge lo hace una persona.
    • Documentación (README/Pages) y FD03 actualizados si cambia un requisito.
