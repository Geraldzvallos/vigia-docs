    1. Fundamentos: ¿Qué es Behavior-Driven Development (BDD)?¶

    El desarrollo guiado por el comportamiento (BDD - Behavior-Driven Development) es un enfoque colaborativo de ingeniería de software que extiende TDD (Test-Driven Development) hacia el negocio. Su propósito principal es eliminar la brecha de comunicación entre las partes interesadas (negocio, analistas, QA y desarrolladores) mediante un lenguaje ubicuo comprensible por personas no técnicas y ejecutable de forma automatizada por el framework de pruebas.

    1.1 El Ciclo BDD¶

    1. Descubrimiento (Discovery): A través de sesiones de refinamiento, el equipo define el comportamiento esperado de una historia de usuario usando ejemplos concretos.
    2. Formulación (Formulation): Los ejemplos se redactan en archivos .feature usando la sintaxis Gherkin, estructurados en la tríada clásica:
    3. Dado (Given): Establece el contexto previo, estado inicial o precondiciones del sistema.
    4. Cuando (When): Describe la acción o evento desencadenado por el usuario o sistema.
    5. Entonces (Then): Comprueba el resultado observable, postcondiciones o efectos colaterales esperados.
    6. Y / Pero (And / But): Conectores de fluidez para encadenar condiciones adicionales.
    7. Automatización (Automation): Los pasos de Gherkin se traducen a código ejecutable en Python (@given, @when, @then) que interactúa con la API REST (TestClient) y la base de datos aislada.

    1.2 BDD en Español (# language: es)¶

    Para Vigía, se configuró la localización oficial de Gherkin al español en cada archivo mediante la directiva # language: es: - Característica: (Feature) - Escenario: (Scenario) - Dado (Given) - Cuando (When) - Entonces (Then) - Y (And)

    2. Relación con las Historias de Usuario (Campo bdd_ref)¶

    En el modelo de datos de Vigía (versión 2.0, tabla acceptance_criteria), cada criterio de aceptación de una historia de usuario cuenta con un campo dedicado denominado bdd_ref.

    Este campo actúa como un puntero de trazabilidad bidireccional viva: 1. Desde la historia de usuario en el portal web o API, el campo bdd_ref indica exactamente qué archivo de feature y escenario automatiza dicho criterio (ej. features/historias_usuario.feature:HU-01). 2. En la suite automatizada, la ejecución del escenario confirma el cumplimiento del criterio de aceptación sin ambigüedades.

    3. Catálogo de Features y Escenarios Implementados¶

    Los archivos de especificación se encuentran ubicados en portal-integrador/tests/acceptance/features/.

    3.1 Feature: historias_usuario.feature¶

    Propósito: Validar el registro de historias de usuario con criterios Dado/Cuando/Entonces, asignación automática de correlativos (HU-01, HU-02), estado inicial PENDIENTE y vinculación no duplicada con casos de prueba del mismo proyecto. - Escenario 1: Registro exitoso de historia con criterios de aceptación estructurados. - Escenario 2: Vinculación de un caso de prueba a una historia de usuario.

    3.2 Feature: corridas_manuales.feature¶

    Propósito: Probar la ejecución de suites manuales, la aplicación de la regla de negocio RN19 (comentario obligatorio al calificar un caso como FALLIDO o BLOQUEADO) y la generación automática de tickets trazables hacia la historia de origen al finalizar la corrida. - Escenario 1: Fallo en caso manual exige comentario obligatorio según regla RN19 (rechazo 422 si falta justificación). - Escenario 2: Finalizar corrida con caso manual fallido genera ticket de defecto trazable con historia y descripción de fallo.

    3.3 Feature: importacion_junit.feature¶

    Propósito: Verificar la ingesta de reportes XML estándar de JUnit (generados por pipelines de CI/CD), creación de corridas automáticas en estado FINALIZADA (origen JUNIT), generación de defectos y la deduplicación estricta que reabre incidentes previamente resueltos sin duplicar filas. - Escenario 1: Importación exitosa de reporte JUnit XML genera corrida consolidada y tickets. - Escenario 2: Reimportación posterior de reporte JUnit no duplica tickets y reabre resueltos.

    3.4 Feature: matriz_trazabilidad.feature¶

    Propósito: Comprobar la generación de la matriz de trazabilidad extremo a extremo que correlaciona requisitos con casos de prueba, resultados de corrida y defectos derivados, evaluando los estados APROBADA, CON_FALLOS y SIN_CASOS. - Escenario 1: Consulta de trazabilidad con historias cubiertas, aprobadas y con fallos.

    3.5 Feature: permisos_roles.feature¶

    Propósito: Validar el gobierno de roles RBAC por proyecto (OWNER, QA, DEV): los desarrolladores no pueden importar resultados externos JUnit (403) y únicamente los propietarios del proyecto (OWNER) tienen privilegios para almacenar claves de cifrado y webhooks hacia GitHub, Discord o Slack. - Escenario 1: Usuario con rol DEV no tiene autorización para importar reportes JUnit. - Escenario 2: Solo el usuario con rol OWNER puede configurar integraciones externas.

    4. Implementación Técnica de los Step Definitions¶

    La implementación de los pasos de prueba se estructuró de forma modular en portal-integrador/tests/acceptance/: - test_bdd_historias_usuario.py - test_bdd_corridas_manuales.py - test_bdd_importacion_junit.py - test_bdd_matriz_trazabilidad.py - test_bdd_permisos_roles.py

    Principios de Aislamiento y Calidad Aplicados:¶

    1. Base de Datos SQLite en Memoria: Cada escenario utiliza una sesión aislada vía conftest.py y setup_isolated_db, evitando efectos secundarios entre pruebas y garantizando que la base de datos local nunca se modifique.
    2. Cero Salidas a la Red: Se emulan las interfaces de red (http_runner._enviar y http_runner._resolver) garantizando que ninguna prueba BDD envíe peticiones HTTP reales a proveedores externos (GitHub, Discord, Slack o APIs de terceros).
    3. Autenticación Fiel: Se generan tokens JWT válidos por usuario y proyecto, verificando cabeceras Authorization: Bearer <token> de forma análoga a la aplicación en producción.

    5. Instrucciones de Ejecución¶

    Ejecutar Únicamente las Pruebas BDD¶

    cd portal-integrador
python -m pytest tests/acceptance -k "bdd" -v

    Ejecutar la Suite Completa con Cobertura¶

    cd portal-integrador
python -m pytest -q -m "not oracle_integration"
