    1. Fundamentos Teóricos: Cobertura vs. Pruebas de Mutación¶

    1.1 ¿Qué es la Cobertura de Código (Code Coverage)?¶

    La cobertura de código es una métrica estructural que determina qué líneas, sentencias o ramas lógicas del código fuente son ejercitadas durante la ejecución de una suite de pruebas automatizadas. - Utilidad: Identifica código muerto, caminos de ejecución no alcanzados y vacíos en los casos de prueba. - Limitación principal: La cobertura mide ejecución, no verificación. Un test puede pasar por el 100% de las líneas de una función sin tener asertos (assert), registrando cobertura perfecta a pesar de no validar ninguna regla de negocio.

    1.2 ¿Qué son las Pruebas de Mutación (Mutation Testing)?¶

    Las pruebas de mutación evalúan la calidad intrínseca y la sensibilidad de la suite de pruebas. El framework de mutación (en Python, mutmut) introduce pequeños cambios sintácticos deliberados ("mutantes") en el código de producción: - Inversión de operadores relacionales (< por <=, == por !=). - Alteración de literales numéricos o cadenas (True por False, +1 por -1, constantes vacías). - Eliminación de llamadas a funciones o sentencias condicionales (if cond: por if True: o if False:).

    Tras inyectar cada mutante, se ejecutan las pruebas: - Mutante Muerto (Killed): Al menos una prueba falló tras la mutación. La suite detectó la anomalía con éxito. - Mutante Sobreviviente (Survived): Todas las pruebas pasaron a pesar del código defectuoso. Indica un aserto débil o ausencia de validación sobre esa condición límite. - Timeout / Inviable: El mutante causó un bucle infinito o un error sintáctico no evaluable.

    El Mutation Score se define como: $$\text{Mutation Score} = \frac{\text{Mutantes Muertos}}{\text{Total Mutantes Evaluables}} \times 100\%$$

    4. Pruebas de Mutación con Mutmut en GitHub Actions¶

    4.1 Justificación Técnica de la Ejecución en Ubuntu (CI)¶

    mutmut utiliza primitivas de bifurcación de procesos (fork), señales UNIX (SIGTERM, SIGKILL) y temporizadores precisos de subproceso para interrumpir mutantes que generan bucles infinitos. En entornos Windows, estas llamadas de sistema no son soportadas de manera nativa por la biblioteca estándar de Python o producen cuelgues del intérprete.

    Por esta razón, se configuró un workflow nativo de Linux en GitHub Actions: .github/workflows/mutation.yml.

    4.2 Características del Workflow .github/workflows/mutation.yml¶

    1. Disparo manual (workflow_dispatch): la mutación es intensiva en cómputo (la corrida completa tarda alrededor de una hora), por eso no se ejecuta en cada push ni en cada pull request.
    2. Sin secretos y con permisos mínimos (contents: read) en cada job.
    3. Acciones fijadas por SHA de 40 caracteres: actions/checkout v7.0.1, actions/setup-python v7.1.0, actions/upload-artifact v7.0.2 y actions/download-artifact v8.0.2.
    4. mutmut fijado en la versión 2.5.1. La primera corrida (run #1, 16/11/2026) instaló mutmut 3, que no acepta --paths-to-mutate: los cinco módulos fallaron al arrancar y no se generó ningún mutante. Se fijó la versión 2.5.1, compatible con esa forma de configurar la mutación.
    5. Un job por módulo, en paralelo (matriz): validator, sql_policy, permissions, ticket_service y validators. Cada job ejecuta solo las pruebas que usan el módulo (se eligen con grep), para que cada mutante tarde segundos.
    6. Consolidación: el job final descarga los resultados de los cinco módulos y scripts/mutacion_resumen.py calcula el mutation score de cada uno y el total, lo publica en el Summary del run y lo sube en el artefacto reporte-mutacion (con mutmut_<modulo>_results.txt, que lista los mutantes sobrevivientes).

    4.3 Cómo Ejecutar la Mutación desde GitHub Actions¶

    1. Ingresar al repositorio → pestaña Actions → «Pruebas de mutación (mutmut)».
    2. Run workflow → rama main → Run workflow.
    3. Al terminar, el resultado aparece en el Summary del run y en el artefacto reporte-mutacion.

    6. Análisis: por qué la mutación difiere de la cobertura¶

    La cobertura de líneas era de 89 % y la de ticket_service de 91 %, pero su mutation score inicial fue de solo 49 %: 153 de sus 300 mutantes sobrevivieron.

    La razón es la diferencia entre ejecutar y verificar:

    • La cobertura cuenta líneas recorridas. ticket_service se recorría casi entero a través de las pruebas de API y de corridas, que crean tickets como efecto secundario.
    • La mutación cuenta resultados verificados. Esas pruebas no comprobaban los detalles del ticket (severidad, estado, transiciones, asignación, deduplicación). Si mutmut cambiaba, por ejemplo, una severidad o una condición de transición, las pruebas seguían pasando: el código se ejecutaba, pero nadie revisaba lo que devolvía.

    Al agregar pruebas que llaman directamente al servicio y verifican cada resultado, los mismos 300 mutantes pasaron de 147 a 290 eliminados (96.7 %). La cobertura casi no cambió; lo que cambió fue la calidad de los asertos. Por eso la mutación complementa a la cobertura: muestra qué partes del código se ejecutan sin que ninguna prueba verifique su comportamiento.

    7. Conclusiones y Plan de Mejora¶

    1. Meta cumplida: el mutation score total pasó de 59.5 % a 86.4 % (555 de 642 mutantes eliminados), por encima de la meta de 70 %.
    2. Cobertura y mutación se complementan: una cobertura de 89 % no garantizaba pruebas efectivas; la mutación encontró el punto débil (ticket_service) y guió las pruebas nuevas.
    3. Pendiente — sql_policy (67.3 %): es el único módulo por debajo de 70 %, con 34 mutantes sobrevivientes. El siguiente paso es revisar mutmut_sql_policy_results.txt y agregar pruebas de valores límite sobre las reglas por entorno (palabras reservadas, CTE, FOR UPDATE).
    4. validator y permissions (75 %): cumplen la meta, pero tienen 14 y 22 sobrevivientes; se revisarán con el mismo procedimiento.
    5. Práctica continua: relanzar mutation.yml antes de cada versión y registrar el resultado en este reporte.
